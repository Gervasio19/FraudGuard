## 1. Scope

- **Phase 4b [D]:** two fixed baselines, a majority-class `DummyClassifier(strategy="prior")` and a `StandardScaler` + `LogisticRegression(class_weight="balanced", C=1.0, solver="lbfgs", max_iter=1000)`. Both are evaluated on the validation partition of Experiment A (chronological, primary) and Experiment B (duplicate-group-aware stratified random, secondary). The features are `V1`–`V28` and `Amount`; `Time` is excluded from the model inputs.
- **Phase 4c [D]:** the Experiment A Logistic Regression only. Max-F1 threshold analysis is run on full validation, then validation is split into two consecutive windows, and the Window 1 threshold is frozen and transferred to Window 2.
- **Not done in either phase [D]:** tuning, feature engineering, resampling, calibration, test-set scoring, or choosing an operational threshold.

## 2. Leakage and isolation (both phases)

- The scaler is fitted inside the pipeline on training rows only. `fit` receives only train rows, and `predict_proba`/`predict` receive only validation rows. Evaluating on test raises an error **[I][V]**.
- No model selection takes place. The two Phase 4b baselines are fixed and reported side by side. Phase 4c fits once and scores once **[I][V]**.
- The Phase 4c window boundary depends only on timestamps. The Window 1 selection uses Window 1 rows only, and flipping the Window 2 labels leaves the transferred threshold unchanged **[I][V]**.
- Test labels appear in the Phase 4b results file as descriptive partition counts only. They were already disclosed in the Phase 3 report, Section 3.4 **[D]**.

### 3.2 Bootstrap confidence intervals [V]

Method: 2,000 resamples, stratified by class within each validation partition, with `numpy.random.default_rng(0)`. The fitted model and its scores were held fixed; only the evaluation rows were resampled. These are independent audit computations; no script was added to the repository.

| Experiment | Logistic Regression average precision | 95% bootstrap interval |
|---|---:|---:|
| A: chronological | 0.8397 | [0.746, 0.922] |
| B: stratified random | 0.7524 | [0.644, 0.857] |

**[R]** The uncertainty is substantial: each interval spans about ±0.09 around its point estimate, which follows from having only 56 and 74 validation frauds. The two intervals overlap heavily. This supports the existing statement in `docs/WORK_LOG.md` that the A–B gap should not be read as evidence that chronological generalization is easier. The two experiments also evaluate different transactions, so they are reported separately and never pooled.

### 3.3 Duplicate overlap (cross-reference: Phase 3 report, Section 5)

- The duplicate key used by both splits is all columns except `Class`, which includes `Time`. The recorded zero cross-partition groups therefore hold under that definition. For the chronological split this is true by construction (Phase 3 report, Section 5.2) **[D]**.
- At the model-input level (`V1`–`V28` + `Amount`), 824 validation rows in Experiment A and 1,510 in Experiment B have an exact twin in train. All are non-fraud with consistent labels **[V]**.
- Measured effect: removing those rows changes Logistic Regression average precision from 0.839660 to 0.839697 (A) and from 0.752375 to 0.752528 (B) **[V]**.
- **[R]** This is duplicate *overlap*, not proven leakage. Identical inputs receive identical scores whatever their partition, and the twins are legitimate repeated records. On this data their measured effect on the ranking metrics is negligible. As in Phase 3, a model-input duplicate checker remains a possible future improvement that needs separate approval.

### 3.4 Probability calibration and the 0.5 rule

- With `class_weight="balanced"`, the Logistic Regression is trained as if both classes were equally frequent. Its probabilities are therefore **not calibrated** to the real fraud rate. On Experiment A validation the mean predicted probability is 0.078, against a prevalence of 0.0013 **[V]**.
- For this reason the 0.5 rule flags 1,309 (A) and 1,002 (B) validation transactions. Precision, recall and the confusion matrix at 0.5 are **diagnostic** metrics only. 0.5 is not an optimal, selected or operational threshold **[D][R]**.
- **Decision-rule correction [V]:** scikit-learn's binary `LogisticRegression.predict` flags a row when the decision function is > 0, which means a probability **strictly greater than** 0.5. Earlier documentation said "≥ 0.5". No validation score equals exactly 0.5 in either experiment, so every reported count is unaffected. By mentor decision, the Phase 4b code and `reports/phase4b_baseline_results.json` (whose `decision_rule_note` says ">= 0.5") are left unchanged. The correction is recorded here and in the project documentation.

The audit rebuilt all three threshold curves with an independent cumulative-count algorithm. Thresholds, counts, F1 values and null patterns were identical to the JSON. The F1 maximum is unique in all three curves, so the lowest-threshold tie-break was never triggered **[V]**.

### 4.2 Window construction [I][V]

- The windows are Window 1, `Time` 132,929–142,280 (21,362 rows), and Window 2, `Time` 142,281–151,328 (21,360 rows). No timestamp group is split across them.
- An exact 21,361 / 21,361 split is impossible without breaking a timestamp group. `Time` 142,280 holds 5 transactions, which take the cumulative count from 21,357 to 21,362. The smallest achievable size difference is therefore 2. The mentor confirmed 21,362 / 21,360 as correct.

### 4.3 Score saturation [V]

The selected thresholds are 4.0×10⁻⁶, 2.2×10⁻⁶ and 4.0×10⁻⁷ below 1.0. That is close to 1.0 but about ten orders of magnitude above floating-point resolution near 1 (1.1×10⁻¹⁶). Validation has 41,807 unique probabilities and 41,807 unique logits, so saturation merged no scores, and selecting on logits gives the same maximum F1. **[R]** Because the probabilities are uncalibrated (Section 3.4), these thresholds are best read as rank cut-offs (the top 17–47 alerts), not as fraud probabilities.

## 5. Temporal stability: frozen-threshold transfer (exploratory)

### 5.1 Bootstrap of the full selection-and-transfer procedure [V]

Method: 2,000 resamples, stratified by class within each window independently, with `numpy.random.default_rng(0)`. In each resample the Window 1 max-F1 threshold is re-selected on the Window 1 sample, applied unchanged to the Window 2 sample, and compared with the Window 2 sample's own max-F1. The model and scores are fixed. These are independent audit computations; no script was added to the repository.

| Quantity | Observed | Bootstrap median | 95% interval |
|---|---:|---:|---:|
| Window 1 selection F1 | 0.8500 | 0.85 | [0.72, 0.95] |
| Transferred Window 2 F1 | 0.8000 | 0.81 | [0.68, 0.90] |
| Gap (transferred − Window 2 retrospective optimum) | −0.0276 | −0.034 | [−0.10, 0.00] |

Supplementary **[V]**: the Window 2 retrospective max-F1 has median 0.85 and interval [0.74, 0.93]. The re-selected Window 1 threshold varies widely across resamples (1 − t from 1.8×10⁻⁷ to 7.2×10⁻⁵). No resample produced a transferred threshold that flagged nothing.

### 5.2 Interpretation [R]

- **The gap is non-positive by construction.** A frozen threshold divides Window 2 into flagged and unflagged rows exactly as one of Window 2's own candidate thresholds would (the smallest Window 2 score at or above it). Window 2's retrospective optimum is the maximum F1 over all those candidates, so the transferred F1 can never exceed it. The only exception is a threshold above every Window 2 score: then F1 is undefined (null), not larger. A negative gap is expected even if nothing changes over time, so its sign carries no information.
- **The size of the gap is not distinguishable from selection optimism.** The observed −0.028 (two extra false positives) lies near the middle of the bootstrap distribution, whose interval runs from −0.10 to 0.00. This single transfer is consistent with a threshold that carries over well, and also with moderate degradation. It does **not** independently establish temporal robustness. Together with the approximately 48-hour coverage of the dataset, this supports the existing wording in `docs/WORK_LOG.md` ("carried over reasonably within this ~48-hour dataset … does not establish long-term temporal robustness"), and nothing stronger.

### 5.3 Fraud prevalence differs between windows [D][R]

Window 1 prevalence is **0.108%** (23 / 21,362) and Window 2 is **0.154%** (33 / 21,360). Precision, and therefore F1, depends on prevalence: at the same ranking quality, a window with more frauds per row tends to give higher precision at a fixed threshold. Raw F1 differences between the windows, such as 0.85 against 0.80, therefore mix any change in model behavior with a change in fraud rate, and with sampling noise from 23 and 33 frauds. They should not be read as direct evidence of drift. The transfer analysis compares the transferred and retrospective F1 *within* Window 2, which avoids the prevalence difference but not the selection optimism described above.

## 6. Common-reference comparison (descriptive) [I]

This comparison was approved during the Phase 4c design discussion and implemented on 2026-11-08 as the output key `common_reference_thresholds` in `reports/phase4c_threshold_results.json`. It is a **separate experiment** from the frozen-threshold transfer in Section 5:

- **Transfer (Section 5, exploratory):** a threshold chosen on Window 1 only is evaluated on unseen Window 2 labels.
- **Common reference (this section, descriptive):** the same two reference thresholds are applied independently to each window, using the scores already computed. Nothing is refitted or rescored. Neither threshold is chosen per window.

Rule: `y_score >= threshold` (the Phase 4c inclusive rule). No validation score equals exactly 0.5, so the 0.5 rows are identical under scikit-learn's strict `predict` rule.

| Reference threshold | Window (prevalence) | TP | FP | FN | TN | Precision | Recall | F1 | Alerts |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 0.5, fixed diagnostic | 1 (0.108%) | 20 | 646 | 3 | 20,693 | 0.0300 | 0.8696 | 0.0581 | 666 |
| 0.5, fixed diagnostic | 2 (0.154%) | 32 | 611 | 1 | 20,716 | 0.0498 | 0.9697 | 0.0947 | 643 |
| 0.999995978456591, full-validation max-F1 (**retrospective**) | 1 (0.108%) | 17 | 0 | 6 | 21,339 | 1.0000 | 0.7391 | 0.8500 | 17 |
| 0.999995978456591, full-validation max-F1 (**retrospective**) | 2 (0.154%) | 26 | 4 | 7 | 21,323 | 0.8667 | 0.7879 | 0.8254 | 30 |

Observations:

- **The full-validation threshold is retrospective and descriptive.** It was selected on full validation, which includes the labels of *both* windows. Its per-window results are not out-of-sample performance for either window **[R]**.
- **Consistency [I][V]:** for each threshold, the window counts sum to the full-validation counts. At 0.5 this gives 52 TP / 1,257 FP / 4 FN, the Phase 4b Experiment A confusion matrix. At the max-F1 threshold it gives 43 / 4 / 13 / 42,662, the full-validation optimum.
- **Identical Window 1 counts [V]:** the full-validation max-F1 threshold (0.999995978…) and the Window 1 optimum (0.999997822…) produce identical Window 1 counts (17 / 0 / 6 / 21,339). No Window 1 score lies between the two thresholds. They differ on Window 2 (26 / 4 / 7 against 24 / 3 / 9).
- **[R]** At 0.5 both windows are flagged at a similar rate (3.1% and 3.0% of rows), with very low precision. This again shows that 0.5 is not a meaningful cut-off for these uncalibrated scores. The F1 values differ between windows partly because of the prevalence difference (Section 5.3), so the table describes the windows; it does not measure drift.

## 7. Limitations

- Validation contains 56 frauds, and the windows 23 and 33. All point estimates carry the wide uncertainty shown in Sections 3.2 and 5.1 **[V]**.
- The dataset covers about 48 hours. Validation and the windows lie in hour values 12–18 of day 2 and contain no night hours (Phase 3 report, Section 4) **[D]**.
- Probabilities are uncalibrated. F1 is an evaluation convention, not a cost function. No operational threshold has been chosen **[D]**.
- The bootstrap intervals hold the fitted model fixed. They reflect evaluation-sample uncertainty only, not variability from refitting on different training data **[R]**.
- The test partition remains untouched. Its scope (hour values 18–23 of day 2, prevalence 0.1217%) must be acknowledged before final evaluation (Phase 3 report, Section 7) **[D]**.
